# RecordSift 0.1 — security assessment and remediation register

**Review started:** 2026-10-31. **Technical reassessment completed:** 2026-10-31. **Release target:** Windows, .NET Framework 4.8, C# 7.3. **Original review baseline:** `release/0.1` at `0d381cdedd882cef5d36ddeabb4f7569f0358ea3`. **Historical post-remediation checkpoint:** `76fb60886b0dcd0d81c3e2a1818e086c7b38cd97` (SEC-XLSX-001/002). **Verified latest source/security checkpoint:** `b3d70300904e1e485e88e3f34ec6a2b88a69e291` after SEC-CSV-001 and SEC-XLSX-003. **Current technical recommendation:** **CONDITIONAL GO** for the Windows/net48 release 0.1 scope after full exact-SHA CI; residual risks and sole-maintainer source-promotion GO under #199 remain separately unapproved. **Promotion to main and public publication remain NO-GO** until their explicit owner decisions. This report is a source-level security review and targeted regression plan, **not penetration-test or fuzz-test certification**.

**Governance:** issue [#199](https://github.com/infoconex/RecordSift/issues/199) remains open. Draft main promotion [#209](https://github.com/infoconex/RecordSift/pull/209) must not be merged. A security remediation changes the integration Git tree, so the previously reviewed promotion PR/head and green jobs cannot certify the new candidate. Do not retarget or update it silently; replace/update the promotion candidate only under fresh owner review. No main/tag/GitHub Release/NuGet publication is authorized.

## Assessment coverage and open verification questions

- **CSV:** malformed and multiline CSV, custom delimiter, decoded-character budget and strict decoding have existing acceptance paths. Issue [#216](https://github.com/infoconex/RecordSift/issues/216) / [PR #217](https://github.com/infoconex/RecordSift/pull/217) added bounded NUnit fixtures with 2,048 tiny rows and 4,096 tiny fields, verifying exact-budget acceptance and atomic one-character-short failure; 394/394 NUnit and four required checks passed on integration `f59be8c7115de196931510bad6c498e6dd793505`; issue closed. They check functional enforcement, **not** peak heap allocation or throughput. Adversarial row/field-count memory profiling remains an evidence gap, not a proved bypass.
- **XLSX:** SEC-XLSX-003 (#218/PR #219) additionally covers XML workbook relationships to BIFF `.bin` spreadsheet parts that the XML-only shared-string preflight would otherwise miss; new bounded regression was RED on test-only SHA `959e2c1228b1af09f796c3f138db8086a46aba64` (actual result `Completed` rather than `Failed`), and the production correction passed all four checks on PR head and squash-integrated SHA `b3d70300904e1e485e88e3f34ec6a2b88a69e291` (398/398 NUnit, 425 public API entries and seven unchanged JSON fixtures). Malformed packages, expansion guard, macro-part rejection, formula cached-value behavior, row/column/cell limits, workbook and worksheet selection have existing tests. Actual ZIP byte counting is merged under #210/#211; #212 separately addresses ExcelDataReader 3.9.0 shared-string preallocation from untrusted `uniqueCount`. Issue #218 / PR #219 addresses the separate source-supported `.bin` relationship path to vendor BIFF record-length allocation; this is a guarded input-format boundary, not a blanket ban on unrelated binary ZIP attachments. Its test-only RED run confirmed acceptance of a harmless hybrid input and four required checks passed on both the PR head and squash-integrated commit. A secure `XmlReader` preflight explicitly prohibits DTDs and external resolution for shared-string inspection; this does **not** certify every downstream vendor XML parser or worst-case heap size. An OpenXML part is data, not automatically executable; no Excel/COM automation is used.
- **Validation:** shared pipeline, mapping-conversion errors, duplicate state, bounded regex, cancellation and fail-fast have dedicated tests. Mapper/callback code remains caller-owned.
- **Reporting:** JSON uses DataContractJsonSerializer for a fixed projection of registered diagnostics and excludes accepted records. CSV is not spreadsheet-safe by design. Arbitrary opaque metadata can include control characters or sensitive content; downstream logs/renderers must handle it contextually.
- **Dependencies/CI:** eleven pinned runtime packages; three Windows Actions workflows with four required check contexts. All four [PR #211](https://github.com/infoconex/RecordSift/pull/211) checks and all four exact post-squash integration checks succeeded, including NUnit/API/advisory audit, independent prerelease+stable consumers and documentation. #212 and #218 subsequently merged with four postmerge green checks; latest integration evidence is Windows run #41273282393 (398 NUnit/API/audit), consumer #41273282403 and docs #41273282432.
- **Unverified:** independent penetration/fuzz testing, actual worst-case heap size under crafted shared strings, complete secret scanning, runtime behavior of every malformed-XML variant, and exhaustive third-party code audits.

## 2026-10-31 supplemental review — SEC-XLSX-003

Issue [#218](https://github.com/infoconex/RecordSift/issues/218) uncovered an additional source-supported path through ExcelDataReader 3.9.0's BIFF shared-string reader, which is outside SEC-XLSX-002's XML-only count guard. A small `.bin` part referenced by a workbook relationship could be accepted; an oversized BIFF record-length header would attempt an allocation before the vendor reader validates available bytes on net48. **No intentionally oversized allocation was run.** Test-only [PR #219](https://github.com/infoconex/RecordSift/pull/219) initially failed in Windows CI on this contract, demonstrating that the library accepted a binary relationship; the same PR now contains a restricted `.rels` preflight that rejects binary spreadsheet-part relationships without rejecting unrelated `.bin` attachments. The finding is **remediated and technically verified** by all four required checks on both exact PR head `2dcd4414bfc7a66783aec489caec5ae2f5609360` and squash integration `b3d70300904e1e485e88e3f34ec6a2b88a69e291`; the integration passed 398/398 NUnit, unchanged 425-entry API compatibility and seven JSON fixtures. The completed XLSX ZIP/shared-string safeguards remain intact. An owner decision on residual risks and a separate source-promotion GO are still required thereafter.

**Current security acceptance recommendation (after SEC-XLSX-003): CONDITIONAL GO**, limited to the reviewed Windows/.NET Framework 4.8 implementation and unpublished 0.1.0 candidate. No other demonstrated unresolved release-blocking security defect was identified in this assessment. Source limits are not strict worst-case process memory or CPU guarantees; malicious-input fuzzing, independent penetration testing, full secret scanning and exhaustive vendor analysis were not performed. SEC-CSV-002, SEC-VAL-001/002, SEC-REPORT-001/002, SEC-DEPEND-001 and SEC-API-001 retain the documented caller/operational boundaries. The sole maintainer must review and explicitly decide remaining residual risks and record a new GO for the exact current promotion candidate under [#199](https://github.com/infoconex/RecordSift/issues/199). Passing CI alone does not authorize promotion. **No merge to main, release tag, GitHub Release, or NuGet publication is approved.**
