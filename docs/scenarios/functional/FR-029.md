# FR-029 — Continue processing after record errors

**Requirement:** [FR-029](../../requirements/functional.md)  
**Tracking issue:** [#30](https://github.com/infoconex/RecordSift/issues/30)  
**Priority:** Must  
**Verification status:** Planned — acceptance execution status and observed evidence are maintained in the traceability matrix.

## Purpose

Real batch imports should not stop entirely because one record contains invalid data.

## Functional requirement

**RecordSift shall:** Continue processing later logical records after record-level validation failures by default.

## Inputs and outputs

- **Inputs:** A sequence of records, validation outcomes and error policy.
- **Outputs:** Valid later records and accumulated diagnostics, or a classified fatal source failure.

## Functional rules

- Preserve ordering of accepted rows and diagnostics.
- Do not treat ordinary validation failures as fatal import failures.
- A fatal source failure may terminate processing and must be surfaced explicitly.
- Summaries must describe completed vs incomplete processing truthfully.

## Dependencies and scope

- **Related requirements:** [FR-027](FR-027.md), [FR-028](FR-028.md), [FR-030](FR-030.md), [FR-031](FR-031.md).
- **Boundary:** Fail-fast mode is a separate Should requirement; recovery from unreadable input cannot be guaranteed.

## Open design decisions

Decide whether certain parser errors are recoverable row-by-row and how partial results are surfaced.

## Acceptance scenarios

### FR-029-SC01 — Continue past a failing row

**Given** an invalid record occurs between two valid records,  
**When** import runs with default continue-on-error behavior,  
**Then** both valid records are accepted and the invalid row has diagnostics.

### FR-029-SC02 — Distinguish fatal input failures

**Given** the input source becomes unreadable during processing,  
**When** import is attempted,  
**Then** a source-level failure is surfaced rather than treating unread data as merely invalid rows.
