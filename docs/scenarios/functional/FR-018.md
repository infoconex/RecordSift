# FR-018 — Validate type conversions

**Requirement:** [FR-018](../../requirements/functional.md)  
**Tracking issue:** [#13](https://github.com/infoconex/RecordSift/issues/13)  
**Priority:** Must  
**Verification status:** Planned — this document is the scenario specification; FR-018-SC01/SC02 are recorded as Automated with observed Windows evidence in the [traceability matrix](../../testing/traceability.md).

## Purpose

Malformed dates and numbers should be reported as data problems without crashing a full batch.

## Functional requirement

**RecordSift shall:** Validate that source data can be converted to its schema-declared type.

## Inputs and outputs

- **Inputs:** Raw decoded field content, target type, culture and error-location metadata.
- **Outputs:** A typed value or an actionable conversion diagnostic.

## Functional rules

- Identify numeric/date/type conversion failures with the original field and row.
- Continue validating other records when configured to continue after errors.
- Do not silently accept lossy conversions or invalid formats as valid values.
- Use the explicit culture and conversion policies shared by all readers.

## Dependencies and scope

- **Related requirements:** [FR-011](FR-011.md), [FR-028](FR-028.md), [FR-029](FR-029.md), [NFR-005](../non-functional/NFR-005.md).
- **Boundary:** General field-length, range and pattern checks have separate requirements.

## Open design decisions

Initial conversion-validation policy is now implemented by the Domain-owned primitive converter (see [ADR 0024](../../engineering/decisions/0024-explicit-primitive-conversion.md)). Invalid or overflowed numeric values and malformed dates use the established `ConversionFailed` diagnostic code, with source-field name, logical row and physical line where available, without disclosing raw data. Explicit culture determines numeric/date parsing, and decimals that would require implicit precision rounding are rejected rather than silently modified. The mapper reports an individual record conversion error and imports valid subsequent rows. Conversion of multiple invalid fields within the same record remains fail-fast under the current typed mapper; other validation requirements govern any broader error-accumulation policy. Exact date-format lists and custom conversion precedence remain deferred.

## Acceptance scenarios

### FR-018-SC01 — Report malformed numeric or date input

**Given** a field contains text that cannot be converted to its declared numeric or date type,  
**When** conversion occurs,  
**Then** a field and source-specific conversion error is recorded while other valid rows remain importable.

### FR-018-SC02 — Preserve valid typed values

**Given** a source field contains valid numeric or date data in the configured culture,  
**When** conversion occurs,  
**Then** no type-conversion error is reported and the typed value is preserved.
