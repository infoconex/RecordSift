# FR-032 — Support cancellation

**Requirement:** [FR-032](../../requirements/functional.md)  
**Tracking issue:** [#33](https://github.com/infoconex/RecordSift/issues/33)  
**Priority:** Should  
**Verification status:** Planned — executable tests have not been implemented.

## Purpose

An application may need to stop long-running imports at the caller's request.

## Functional requirement

**RecordSift shall:** Support cancellation of import processing at documented cancellation points.

## Inputs and outputs

- **Inputs:** Import configuration and a caller-provided cancellation signal.
- **Outputs:** An explicit canceled outcome, preserving or discarding partial data according to the contract.

## Functional rules

- Observe cancellation without claiming a fully completed import.
- Do not continue processing indefinitely after cancellation is requested.
- Distinguish cancellation from input errors and record-validation failures.
- Do not leak file handles when cancellation terminates processing.

## Dependencies and scope

- **Related requirements:** [FR-029](FR-029.md), [FR-030](FR-030.md), [FR-033](FR-033.md).
- **Boundary:** Should scope; asynchronous execution is separately deferred to FR-033.

## Resolved design decisions

FR-032 adds additive synchronous `CancellationToken` overloads to Application CSV and XLSX importers, the encoded CSV stream adapter, and shared Application validation pipeline. Existing overloads and default behavior continue to work unchanged. No asynchronous API, cancellation-specific vendor type, package or new Domain port is introduced.

**Checkpoint semantics:** a pre-canceled token returns `Canceled` with zero processed records without opening or reading source content. Cancellation is rechecked after eager source parsing, while materializing format-neutral rows and before each logical row's validation, and after the last logical row before return. Cancellation signaled inside a mapper/validator is observed no later than the subsequent record boundary; the current record's validation finishes first. Already-processed accepted CLR records and any prior record diagnostics are retained, with `ProcessedCount = AcceptedCount + RejectedCount`; unprocessed rows are excluded. Cancellation does not synthesize an error diagnostic and is not a parser error, source failure, or early validation `Stopped` outcome. A noncanceled import remains `Completed` (or the ordinary source failure/validation stop). Caller-owned source readers and streams remain open according to existing ownership contracts.

**Bounded eager-source limitation:** current CSV and XLSX readers materialize the complete bounded source before shared row validation, so a cancellation requested during parser I/O is observed **after the parser returns**, not by forcibly interrupting an in-progress read. Cancellation before source reading and cancellation during per-record validation are supported. Mid-read interruption belongs to future streaming interfaces (FR-034), not the 0.1 promise. Synchronous `.NET Framework 4.8` imports remain independent of FR-033 asynchronous APIs.

A canceled import uses Domain `ImportStatus.Canceled` and `ImportResult.Canceled` with sanitized, resource-backed display messages. JSON reporting emits schema version **1.2** only for `Canceled`; existing version 1.0 `Completed`/`Failed` and version 1.1 `Stopped` reports remain unchanged. See [versioned result contract](../../specifications/import-result.md) and [JSON v1.2 schema](../../specifications/schemas/import-result-canceled.schema.json).

## Acceptance scenarios

### FR-032-SC01 — Honor cancellation during import

**Given** a cancellation request arrives while records are being processed,  
**When** the operation checks cancellation,  
**Then** processing stops with an explicit canceled outcome, not a success summary.

### FR-032-SC02 — Complete without cancellation

**Given** no cancellation is requested during a valid import,  
**When** import completes,  
**Then** all valid rows are returned normally.
