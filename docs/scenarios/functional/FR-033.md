# FR-033 — Support asynchronous processing

**Requirement:** [FR-033](../../requirements/functional.md)  
**Tracking issue:** [#34](https://github.com/infoconex/RecordSift/issues/34)  
**Priority:** Future  
**Verification status:** Planned — executable tests have not been implemented.

## Purpose

Asynchronous APIs can support high-concurrency consumers and nonblocking data sources.

## Functional requirement

**RecordSift shall:** Expose an asynchronous import operation whose records and errors preserve synchronous behavior.

## Inputs and outputs

- **Inputs:** An asynchronous input source or import request and cancellation token.
- **Outputs:** Awaitable import result equivalent to the synchronous contract, or a classified canceled/failure outcome.

## Functional rules

- Maintain schema and validation semantics across sync and async operations.
- Propagate cancellation without false success.
- Avoid hiding synchronous blocking operations behind superficial async wrappers.
- Preserve accepted-record and diagnostic ordering.

## Dependencies and scope

- **Related requirements:** [FR-026](FR-026.md), [FR-029](FR-029.md), [FR-032](FR-032.md), [FR-036](FR-036.md).
- **Boundary:** Future scope; asynchronous API is not required for the initial release.

## Open design decisions

Evaluate true asynchronous capabilities of chosen CSV/XLSX dependencies and define fallback behavior.

## Acceptance scenarios

### FR-033-SC01 — Import asynchronously

**Given** an asynchronous source supplies valid records,  
**When** the async import API is awaited,  
**Then** records and diagnostics match synchronous import semantics.

### FR-033-SC02 — Cancel an asynchronous import

**Given** a cancellation token is signaled while asynchronous import is active,  
**When** the cancellation is observed,  
**Then** the import terminates without misreporting full success.
