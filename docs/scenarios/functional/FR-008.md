# FR-008 — Provide extensible input format interfaces

**Requirement:** [FR-008](../../requirements/functional.md)  
**Tracking issue:** [#11](https://github.com/infoconex/RecordSift/issues/11)  
**Priority:** Future  
**Verification status:** Planned — executable tests have not been implemented.

## Purpose

Additional formats should reuse the common pipeline rather than replicate validation logic.

## Functional requirement

**RecordSift shall:** Define extension points for supplying logical records from additional input readers.

## Inputs and outputs

- **Inputs:** A reader implementation and shared schema/validation settings.
- **Outputs:** Records and errors governed by RecordSift's established import contracts.

## Functional rules

- Readers provide stable source-location metadata.
- A reader failure must not be misreported as a valid empty result.
- Do not expose third-party parser types as part of the long-term core interface.

## Dependencies and scope

- **Related requirements:** [FR-001](FR-001.md), [FR-002](FR-002.md), [FR-009](FR-009.md), [FR-028](FR-028.md), [FR-036](FR-036.md).
- **Boundary:** Deferred format-reader extensibility, not an arbitrary plug-in execution system.

## Open design decisions

Specify lifecycle, error signaling and versioning only when the requirement is scheduled.

## Acceptance scenarios

### FR-008-SC01 — Use a custom record reader

**Given** a third-party reader conforms to the published reader interface,  
**When** the import pipeline consumes its records,  
**Then** mapping and validation use the same result and diagnostic contracts.

### FR-008-SC02 — Handle reader failures

**Given** a custom reader reports an input error,  
**When** the pipeline receives that error,  
**Then** the error is represented as a source failure without being mistaken for a valid row.
