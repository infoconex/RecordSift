## Purpose

Some business constraints depend on relationships between multiple columns.

## Functional requirement

**RecordSift shall:** Allow validators to examine more than one field in the same imported record.

## Inputs and outputs

- **Inputs:** A typed record, declared cross-field rule and available source metadata.
- **Outputs:** A record-level or field-linked diagnostic if related values violate the rule.

## Functional rules

- Run cross-field rules only when their prerequisite values are available under the chosen policy.
- Report which related fields are implicated when practical.
- Allow a valid combination without producing a validation error.
- Follow normal record acceptance and error accumulation semantics.

## Dependencies and scope

- **Related requirements:** [FR-011](FR-011.md), [FR-022](FR-022.md), [FR-028](FR-028.md).
- **Boundary:** Should scope; checks involving external records or services are not included.

## Open design decisions

FR-024 uses the existing Domain-owned `RecordValidationRule<T>` and the same shared CSV/XLSX Application validation pipeline as FR-022; it does not introduce a second validator contract or package. Each rule receives the fully converted, typed record `T`, so a predicate can compare any of its members (for example, a start and end numeric or date value). Callers register these predicates through the existing importer `customRules` constructor argument. Registration order is retained in an immutable snapshot; rules execute after required-value, field-length, regular-expression, typed conversion and range checks, and before duplicate detection. A record with any earlier stage failure (including failed conversion) skips the cross-field predicates; later records still run normally.

Each predicate returning `false` produces one standard, sanitized `VALIDATION_FAILED` diagnostic. Use `field: null` for a whole-record relationship; optionally register a field-linked predicate to associate a single declared source field with a failure. The current contract has no multi-field diagnostic list, and FR-024 does not require inventing one: a caller can register multiple field-linked rules when suitable. Multiple failures on the same row are accumulated in registration order while the row is rejected only once; logical and available physical source provenance are preserved. No sensitive values or arbitrary predicate-produced diagnostic strings are exposed.

Missing optional values are represented by the mapped model's nullable/default members, with any configured default applied before conversion. The caller chooses the appropriate predicate policy, such as `!record.End.HasValue || record.Start <= record.End.Value`. A missing required value or invalid conversion does not invoke the predicate. Expected relationship violations return `false` and are ordinary diagnostics; unexpected predicate exceptions propagate as programming/runtime failures rather than being disguised as source errors. Predicates should be deterministic, side-effect-free and thread-safe if an importer is reused concurrently. These decisions follow [ADR 0029](../../engineering/decisions/0029-domain-custom-record-validation.md) and preserve FR-022 behavior.

## Acceptance scenarios

### FR-024-SC01 — Reject inconsistent related fields

**Given** a record contains mutually inconsistent date or numeric fields,  
**When** the cross-field rule executes,  
**Then** the result includes a record-level validation diagnostic.

### FR-024-SC02 — Accept consistent fields

**Given** the record fields satisfy their cross-field rule,  
**When** the rule executes,  
**Then** no cross-field violation is reported.
