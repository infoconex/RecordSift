# FR-017 — Validate required fields

**Requirement:** [FR-017](../../requirements/functional.md)  
**Tracking issue:** [#9](https://github.com/infoconex/RecordSift/issues/9)  
**Priority:** Must  
**Verification status:** Planned — this document specifies the approved behavior; observed execution evidence is recorded in the traceability matrix.

## Purpose

Incomplete mandatory business data must not enter accepted output records.

## Functional requirement

**RecordSift shall:** Validate fields marked required and identify missing or unacceptable values.

## Inputs and outputs

- **Inputs:** A field value, requiredness policy and source provenance.
- **Outputs:** A field-specific required-value diagnostic or a successful requiredness check.

## Functional rules

- Treat missing required data as a record-validation error.
- Identify both logical record and failing schema field.
- Do not report errors for nonempty valid required values.
- Apply any whitespace/empty policy consistently with optional-field semantics.

## Dependencies and scope

- **Related requirements:** [FR-012](FR-012.md), [FR-028](FR-028.md), [FR-029](FR-029.md).
- **Boundary:** Required source column absence is schema-binding behavior rather than a record-level missing-value failure.

## Release 0.1 required-value policy

An `ExpectedColumn` still declares whether its source **column** is required via `IsRequired`. It independently enables per-record **value** validation through the new opt-in `IsValueRequired` constructor argument, which defaults to `false` to preserve existing behavior.

For a present required-value field, null, empty and whitespace-only text fail. Nonempty data passes the required-value check unchanged; conversion and other validation requirements may still reject it. A missing optional source column does not cause a record-level required-value error. A missing required source column is classified as a source/schema problem by header/position binding, not as an invalid row.

The Domain-owned `ImportSchema.ValidateRequiredValues` evaluates declared fields in schema order using ordinal exact-case names and emits sanitized `REQUIRED_FIELD_MISSING` record diagnostics with original source-field name, logical row and physical CSV line when known. The importer rejects rows with such diagnostics *before* invoking the caller's property mapper. Multiple required-field errors remain independent while the row is counted as rejected once. These rules are independent of any CSV/XLSX parser and do not imply automatic trimming or conversion.

## Open design decisions

The initial policy fixes whitespace handling and deterministic diagnostic ordering. More advanced nullable, normalization, conditional-required and trimming policies remain independent future decisions; no automatic rewriting of source values is implied.

## Acceptance scenarios

### FR-017-SC01 — Reject missing required values

**Given** a required field is missing or blank according to its policy,  
**When** field validation runs,  
**Then** a required-value diagnostic identifies that field and record.

### FR-017-SC02 — Accept an explicitly present value

**Given** a required field contains a valid nonempty value,  
**When** field validation runs,  
**Then** the required-field rule does not reject the row.
