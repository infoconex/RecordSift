# FR-038 — Export validation errors as CSV

**Requirement:** [FR-038](../../requirements/functional.md)  
**Tracking issue:** [#39](https://github.com/infoconex/RecordSift/issues/39)  
**Priority:** Should  
**Verification status:** Planned — legacy specification-planning metadata only; scenario acceptance is determined from observed CI in [traceability](../../testing/traceability.md).

## Purpose

Integrations can export the diagnostic portion of an existing typed import result to a portable, deterministic CSV report without reading the original CSV/XLSX source again.

## Functional requirement

**RecordSift shall:** Export the existing validation diagnostics into CSV with stable field headings, reversible escaping, and no reprocessing of the original source.

## Inputs and outputs

- **Inputs:** An existing typed import result and an optional reporting delimiter.
- **Outputs:** A deterministic CSV text report containing the original ordered, escaped, structured diagnostic rows, or a header-only report when no errors exist.

## Functional rules

- Use correct reversible quoting for commas, configured delimiters, double quotes, CR and LF in all diagnostic columns.
- Do not re-read the original source or export accepted CLR records or caller status text.
- Keep source, record, field and optional worksheet and physical location fields aligned with structured diagnostics.
- Emit the stable nine-column header even for zero diagnostics; preserve original diagnostic order and invariant integer formatting.
- Sanitize rooted source paths and file URIs using the established JSON reporting policy without modifying source diagnostic provenance.

### Public contract

`RecordSift.Infrastructure.Reporting.CsvImportResultSerializerAdapter` implements the existing `RecordSift.Application.Ports.Reporting.IImportResultSerializer` application port. Construct with no arguments for a comma delimiter, or supply a single delimiter character. `Serialize<T>(TypedImportResult<T>)` returns a .NET string; no file I/O, source processing, async, or new Domain contracts are introduced. A null result is rejected.

### CSV wire shape

Exactly nine case-sensitive columns in this order:

```text
SourceId,Scope,Row,Field,Code,Message,Worksheet,PhysicalRow,PhysicalLine
```

- The first record is **always** the header, followed by exactly one record per source or record diagnostic in the original collection order.
- Every record ends with CRLF, including the header and last diagnostic. Embedded original CR/LF characters inside a value are preserved.
- Text containing the selected delimiter, a double quote, CR, or LF is enclosed in double quotes; embedded double quotes are doubled. This allows independent conforming CSV readers to reconstruct each value.
- `SourceId` is the same caller-owned opaque ID used in the existing JSON reporting adapter, including redaction to `source-redacted` for absolute paths and file URIs. It appears on each diagnostic row.
- `Scope` is `Record` or `Source`. `Row` is the invariant-culture one-based logical data row number for a record diagnostic; it is empty for source diagnostics. `Code` and `Message` preserve the registered Domain diagnostic code and its safe resource-backed message.
- Missing optional `Field`, `Worksheet`, `PhysicalRow` and `PhysicalLine` are **empty CSV fields**. Physical coordinates use invariant integer text; no placeholder text is invented.
- All `Completed`, `Failed`, `Stopped` and `Canceled` outcomes are supported. This is an **error-only diagnostic report**, so no status/summary/accepted-record columns are added, and serialization does not change the result or its meaning.

**Empty report policy:** for zero diagnostics, regardless of outcome, emit exactly the single header record ending in CRLF, and no fabricated diagnostic rows.

**Delimiter and encoding:** the default delimiter is comma; a caller may choose a different single character (e.g. semicolon, pipe, or tab). A double quote, CR, LF, NUL or other control character except tab is invalid. The interface returns text rather than bytes, so there is no misleading encoding option in the API. The caller chooses file encoding; **UTF-8 without BOM** is recommended when persisting the returned string. Non-ASCII characters are preserved in the returned string. This does not change source-import encoding configuration.

**Confidentiality boundary:** the adapter never accesses or emits accepted CLR records, caller result status message, or original input values. Registered Domain diagnostics have fixed safe messages. As with JSON reporting, `SourceId` redacts rooted paths/file URIs; caller-selected field/worksheet identifiers and safe opaque IDs are metadata and are not generally scrubbed. Callers must not embed confidential record data in such metadata. Importers should not treat arbitrary CSV field names as spreadsheet-safe formulas; consumers must parse this as CSV data rather than execute untrusted spreadsheet expressions. Preservation of actual identifiers takes precedence over silent mutation in this contract.

## Dependencies and scope

- **Related requirements:** [FR-028](FR-028.md), [FR-036](FR-036.md), [FR-037](FR-037.md).
- **Boundary:** No file delivery service, Excel styling, report-format templates (FR-039), new input format, or asynchronous import work is included.

## Open design decisions

All FR-038-specific release decisions are resolved in the normative CSV wire contract above: stable nine-column headers, CRLF rows, header-only empty exports, a configured character delimiter, and caller-selected text-to-byte encoding. Any future spreadsheet-specialized output or configurable report templates require a separately reviewed requirement.

## Acceptance scenarios

### FR-038-SC01 — Export escaped diagnostics

**Given** an import result contains errors with commas, quotes, or newlines in human-readable messages,  
**When** diagnostics are exported to CSV,  
**Then** stable headers and correctly escaped rows allow another CSV reader to reconstruct the messages.

### FR-038-SC02 — Export an error-free result

**Given** an import produces no diagnostics,  
**When** error-only CSV export is requested,  
**Then** output follows the documented empty-export policy and contains no invented errors.
