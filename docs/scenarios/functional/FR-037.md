# FR-037 — Support readable error summaries

**Requirement:** [FR-037](../../requirements/functional.md)  
**Tracking issue:** [#38](https://github.com/infoconex/RecordSift/issues/38)  
**Priority:** Must  
**Verification status:** Planned — executable tests have not been implemented.

## Purpose

A human-readable explanation helps developers diagnose failed imports without inspecting raw structures.

## Functional requirement

**RecordSift shall:** Produce concise plain-language summaries of an existing import result.

## Inputs and outputs

- **Inputs:** In-memory summary counters and sanitized diagnostics.
- **Outputs:** A readable summary that accurately describes accepted/rejected records and reasons.

## Functional rules

- Explain failures using available row and field context.
- Do not include raw sensitive source values by default.
- Accurately describe clean imports and zero-row results.
- Provide an informational summary for successful zero-record imports without treating the absence of records as an error.
- Describe failed imports using a human-readable error explanation; never make message parsing the only way to identify outcome status.
- Derive output from the result without reopening the source.

## Dependencies and scope

- **Related requirements:** [FR-028](FR-028.md), [FR-030](FR-030.md), [FR-036](FR-036.md), [NFR-008](../non-functional/NFR-008.md).
- **Boundary:** Should not be treated as localized UI presentation or a substitute for structured diagnostics.

## Open design decisions

Resolved by [ADR 0031](../../engineering/decisions/0031-invariant-readable-import-reporting.md). Release 0.1 formatting uses invariant English messages stored in the Reporting adapter's resource catalog. A replaceable Infrastructure implementation behind the Application `IImportResultFormatter` port formats existing Domain counts, statuses and sanitized diagnostics; no source reread or independent rejection logic is allowed. Readable results include logical row and field provenance, diagnostic code/reason and available source location, but never raw accepted records, caller result messages or potentially path-like source identifiers. Explicit per-culture presentation is deferred.

## Acceptance scenarios

### FR-037-SC01 — Explain failed rows

**Given** an import result contains invalid rows,  
**When** a human-readable summary is requested,  
**Then** the summary identifies failed row locations and reasons while omitting raw sensitive values.

### FR-037-SC02 — Summarize a clean import

**Given** a result has no errors,  
**When** a summary is requested,  
**Then** the summary accurately communicates successful processing without invented failures.

### FR-037-SC03 — Explain empty success and missing-header failure distinctly

**Given** a successful header-only or headerless zero-byte CSV import with no records,  
**And** a failed zero-byte CSV import that required a header row,  
**When** human-readable summaries are requested for both results,  
**Then** the successful result reports that no records were found without raising an error solely for emptiness,  
**And** the failed result explains that required header information was missing,  
**And** machine-readable outcome state is independently available so callers do not need to parse message text.
