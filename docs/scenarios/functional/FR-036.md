# FR-036 — Expose structured in-memory results

**Requirement:** [FR-036](../../requirements/functional.md)  
**Tracking issue:** [#37](https://github.com/infoconex/RecordSift/issues/37)  
**Priority:** Must  
**Verification status:** Planned — executable tests have not been implemented.

## Purpose

The library must expose usable results without forcing callers to parse exported reports.

## Functional requirement

**RecordSift shall:** Expose a structured in-memory representation of import outcomes.

## Inputs and outputs

- **Inputs:** An import's accepted typed records, diagnostics and processing summary.
- **Outputs:** A typed result object that callers can inspect independently of JSON output.

## Functional rules

- Provide access to accepted records, structured diagnostics and aggregate counts.
- Maintain consistency between row classification and counter values as documented in [the import result contract](../../specifications/import-result.md): `rejectedCount` and `warningRowCount` each count distinct affected rows, not individual findings.
- Distinguish completed imports from fatal or canceled outcomes.
- Do not require JSON serialization or filesystem output for normal use.

## Dependencies and scope

- **Related requirements:** [FR-027](FR-027.md), [FR-028](FR-028.md), [FR-030](FR-030.md), [FR-035](FR-035.md).
- **Boundary:** Persistence and UI presentation are consumer responsibilities.

## Open design decisions

Define result immutability, lazy vs eager collections, and result shape for partial/fatal imports.

## Acceptance scenarios

### FR-036-SC01 — Expose accepted records and diagnostics

**Given** an import completes with valid and invalid source records,  
**When** the caller reads the result object,  
**Then** typed accepted records, diagnostic details, and aggregate counts are accessible without parsing JSON.

### FR-036-SC02 — Preserve result consistency

**Given** a record contains multiple diagnostics,  
**When** the result is inspected,  
**Then** `rejectedCount` counts the affected record once regardless of how many error-level diagnostics exist,  
**And** `warningRowCount` counts any warning-bearing row once, even when that row is also rejected,  
**And** all individual error and warning diagnostics remain accessible separately without an ambiguous row-level `errorCount`.
