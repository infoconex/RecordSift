# RecordSift 0.1.0 — publication execution and verification

**Release scope:** Windows only, .NET Framework 4.8, C# 7.3. MIT, Copyright (c) 2026 Infoconex. This is the first stable RecordSift release. Source promotion [PR #244](https://github.com/infoconex/RecordSift/pull/244) completed at `main` `9ba0c3be740fea3b8f350648d43ec5341a34b2aa`, with all four new-main checks successful and 419 routine NUnit discoveries (418 pass, zero failure, one explicitly skipped). **Publication source SHA must be the exact current `main` SHA chosen below, not an earlier milestone.** The following are explicit manual publication steps, not evidence that a public upload has already occurred.

## 1. Source and owner release gates

1. Review the final 0.1.0 delta and security assessment, including documented eager parsing/resource/cancellation limits, external vendor exposure, caller-controlled callbacks and identifiers, and machine-interchange-only diagnostic CSV spreadsheet-formula risk. The owner accepted that CSV behavior in [issue #200](https://github.com/infoconex/RecordSift/issues/200); do not infer acceptance of every other residual risk. Record dated owner publication GO and any remaining risk acceptance in [governance issue #199](https://github.com/infoconex/RecordSift/issues/199). Assistant-authored audit notes are not an independent human code review.
2. Confirm the source `main` HEAD, active squash-only ruleset, and **four success check runs on that exact HEAD**: Windows NUnit/API, pinned NuGet vulnerability audit, installed RC/stable consumer, and requirements/docs. Stop for a missing/failing check, fresh blocking advisory, altered source tree or unresolved publication risk.
3. Confirm package ownership and ID `RecordSift` at nuget.org through the authorized publishing account. First publication establishes initial package ownership. Do not use a different package ID without updating the manifest and re-running acceptance.
4. Inspect the final source tree for credentials, private identifiers and sensitive fixtures. The bounded automated tests and dependency audit do not constitute an exhaustive security or secret-scanning certification. Never put a publishing API key in the repository, job logs, PR or conversation.

## 2. Build and retain one exact stable artifact

On GitHub, go to **Actions → Prepare verified 0.1.0 publication artifact → Run workflow**, select **main**, and supply the complete 40-character **current `main` HEAD** in `source_sha`. The workflow refuses stale/main-mismatched SHAs, verifies all four exact-SHA checks, restores pinned dependencies, compiles Release net48, builds **`RecordSift.0.1.0.nupkg`**, checks its packaged version/MIT/README/notice/repository `main` and exact commit metadata, installs and runs an independent Windows consumer from its local feed, and stores an artifact named `recordsift-0.1.0-publish-ready-<SHA>`.

Download that GitHub Actions artifact and extract **the original `.nupkg`** plus `SHA256SUMS.txt` and `SOURCE_COMMIT.txt`. The enclosing GitHub Actions artifact ZIP is not the NuGet package. On Windows PowerShell, verify the source identity and local package digest:

```powershell
Get-Content .\SOURCE_COMMIT.txt
Get-Content .\SHA256SUMS.txt
(Get-FileHash .\RecordSift.0.1.0.nupkg -Algorithm SHA256).Hash.ToLowerInvariant()
```

Compare the full digest and exact source SHA to the workflow's printed verification and manifest. **Retain the original nupkg and its recorded SHA256** as the upload source-of-truth. Do not rebuild a second untracked package for public upload; ZIP timestamps can change package bytes.

## 3. Stage a GitHub release against the same source

On **GitHub → Releases → Draft a new release**, choose the new tag **`v0.1.0`**, ensure its target is the **exact source SHA** recorded in `SOURCE_COMMIT.txt` on `main`, give the release title **`RecordSift 0.1.0`**, and adapt [release notes](0.1-release-notes.md) to explain the Windows/net48 supported scope, major capabilities, known limitations and exact artifact provenance. Attach the verified original `RecordSift.0.1.0.nupkg` and `SHA256SUMS.txt`; save as **Draft** until the public feed is verified. Do not point the tag to an earlier RC, PR test merge, or `release/0.1` branch.

Creating a draft tag/release is a release-owner action and requires GitHub release permissions; the currently connected GitHub integration does not expose a tag or Release creation action. Record its actual URL only after GitHub confirms creation.

## 4. Upload the exact artifact to nuget.org

After owner publication GO, sign into the nuget.org account authorized to own `RecordSift`. Use **Upload Package** and select the verified original `RecordSift.0.1.0.nupkg`. Review the displayed stable version, Windows/net48 dependency group (eleven pinned packages), MIT license, README, repository metadata and package ID before confirming publication. Alternatively, use a scoped nuget.org API key through your own secure Windows environment:

```powershell
nuget push .\RecordSift.0.1.0.nupkg -Source https://api.nuget.org/v3/index.json -ApiKey $env:NUGET_API_KEY -NonInteractive
```

The environment variable must be provisioned privately outside chat and GitHub source. Never check it in or print it. **NuGet package IDs/versions are immutable once published**; if validation finds a defect, stop public rollout and correct with a new version rather than silently overwrite `0.1.0`.

## 5. Verify the actual published package (different from local preflight)

After NuGet indexes the version, independently install **`RecordSift 0.1.0` from nuget.org alone** into a fresh Windows/net48 C# 7.3 consumer, not from the local prepublication feed. Verify representative CSV and XLSX imports, mapping, validation and all report formats; check the five assemblies/XML docs, dependency versions, the public license/notices and effective package repository commit. Run `nuget verify -Signatures` (or a supported NuGet signature-verification equivalent) against the nuget.org-downloaded package.

**Important:** nuget.org repository-signs hosted packages and can modify the archive by adding a signature. A downloaded `.nupkg` may therefore have a different *whole-file* SHA256 from the prepublication upload. Preserve and report **both** hashes; compare normalized package contents/metadata and individual assembly hashes, and validate the NuGet repository signature rather than declaring corruption based solely on the changed archive SHA256.

Only after public-feed checks pass should the owner **publish** the staged GitHub Release. Record the final immutable `v0.1.0` tag SHA, GitHub Release URL, nuget.org package URL, prepublication/upload SHA256, published/download SHA256, signature result and public-feed consumer CI evidence on issue #199; then close #199 and #245 if all gates are truly satisfied and the owner review/sign-off is documented.

## 6. Halt / recovery

If any main test, packaging, licensing, vulnerability, identity, secret-scan or independent consumer check fails, keep the GitHub Release Draft and **do not push** the NuGet package. If a problem is discovered after package publication, halt further rollout, document the affected immutable version and hashes, warn consumers via the release page/issues and publish a corrected version only after new reviewed tests and owner GO. Preserve evidence; never force-push or delete a historical tag to hide a published defect.

**No automated publication credentials are configured or invoked by the preparation workflow.** Public release requires the explicitly authenticated GitHub and nuget.org operations in steps 3–5.
