# FR-025 — Support configurable validation severity

**Requirement:** [FR-025](../../requirements/functional.md)  
**Tracking issue:** [#26](https://github.com/infoconex/RecordSift/issues/26)  
**Priority:** Should  
**Verification status:** Planned — executable tests have not been implemented.

## Purpose

Not every undesirable input condition should reject a record; some are advisory.

## Functional requirement

**RecordSift shall:** Allow validation diagnostics to carry a configured severity such as warning or error.

## Inputs and outputs

- **Inputs:** Severity configuration, validation rule and triggering record.
- **Outputs:** Diagnostics with the assigned severity and correct aggregate counts.

## Functional rules

- Preserve severity in structured and reported diagnostics.
- Warnings alone do not reject an otherwise valid record under the documented default contract.
- Error-level failures reject the affected record.
- Summary counters are row-oriented: multiple warnings on one row contribute once to `WarningRowCount`, and one or more errors on a row contribute once to `RejectedCount`.
- A rejected row may also contribute to `WarningRowCount` when it contains warnings.
- Missing optional values do not generate warnings automatically; an advisory rule must be explicitly configured.

## Dependencies and scope

- **Related requirements:** [FR-022](FR-022.md), [FR-027](FR-027.md), [FR-030](FR-030.md).
- **Boundary:** Should scope; user-defined arbitrary severity hierarchies are not assumed.

## Open design decisions

Clarify severity customization and any policy for treating warnings as errors.

## Acceptance scenarios

### FR-025-SC01 — Return configured warnings and errors

**Given** validation rules are assigned warning or error severity,  
**When** rules evaluate the record,  
**Then** each diagnostic preserves its configured severity,  
**And** each affected row contributes at most once to the corresponding row-oriented summary counter.

### FR-025-SC02 — Do not reject solely on warnings

**Given** a record triggers only warning-level validation diagnostics,  
**When** processing completes,  
**Then** the record remains accepted according to the documented result contract.


### FR-025-SC03 — Warn on an optional field only when explicitly configured

**Given** the `Phone` field is optional and a business rule is configured to warn when it is missing,  
**And** a valid customer row has no phone number,  
**When** the row is validated,  
**Then** the row remains accepted,  
**And** the result includes a warning such as `OPTIONAL_VALUE_MISSING`,  
**And** `WarningRowCount` increases by one,  
**And** without the explicitly configured rule, a missing optional field produces no advisory diagnostic by default.
