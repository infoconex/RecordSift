# Release 0.1 readiness, promotion and rollback procedure

## Technical release-candidate verification

1. Record the precise release/0.1 HEAD SHA and freeze Must/targeted Should functionality.
2. From a clean Windows environment, use NuGet.Config restore and Release MSBuild (Any CPU). Run all NUnit suites (379 baseline plus any additions), public API baseline, seven JSON fixtures, XML documentation positive/negative checks, Roslyn naming guard and architecture/resource/diagnostics tests.
3. Verify the NuGet dependency audit and pinned versions; any NU1900–NU1905 warnings or inaccessible audit source require investigation.
4. Create both unpublished `RecordSift.0.1.0-rc.1.nupkg` (default) and the **unpublished stable candidate** `RecordSift.0.1.0.nupkg` (`scripts/build_release_candidate.ps1 -PackageVersion 0.1.0`) locally, in separate temporary folders. The package builder verifies the exact effective version inside the nuspec, five RecordSift DLLs, five XML docs, staged NuGet README, MIT SPDX expression, exact root LICENSE and THIRD-PARTY-NOTICES.md, exact declared dependencies and 0.1.0.0 assembly/file versions.
5. Install **each version** in a separate Windows net48 consumer from its own local feed (`verify_clean_consumer.ps1 -PackageVersion 0.1.0` for stable); compile and execute only against package-managed assemblies. Verify CSV, XLSX, validation, structured results, JSON, readable and CSV diagnostic reporting.
6. Reconcile consumer README, release notes, supported platforms, limitations, JSON contract, source security and runtime package dependencies with actual observed behavior.
7. Record the owner's approved **MIT** project license and **Copyright (c) 2026 Infoconex** (#186), verify the source LICENSE, exact NuGet SPDX license expression and included third-party notices against the eleven pinned packages; rebuild/retest the exact package. Examine repository for secrets/sensitive test data before any distribution.
8. Confirm all relevant Windows, documentation, consumer and security jobs green at the final integration HEAD and document a GO / CONDITIONAL GO / NO-GO assessment with evidence and unresolved risks.

## Mandatory solo-maintainer review and sign-off before future promotion or publication

[Full policy and verification record](../engineering/release-gates.md); [release 0.1 preliminary audit and open risks](../engineering/release-0.1-prepublication-audit.md). This replaces any implication that technical CI or a 100%-file documentation inventory alone suffices for a GO decision.

1. Verify active `main` branch ruleset requiring a PR, squash-only merges and all four mandatory CI job status checks; these were confirmed in [ruleset #26295899](https://github.com/infoconex/RecordSift/rules/26295899) on 2026-10-31. **Zero** required GitHub reviewer approvals is intentional because the project has one maintainer. A missing required CI check remains **NO-GO**.
2. Record exact candidate SHA and freeze. The **sole maintainer** must perform a second-pass, risk-focused review of production code, security/edge cases, public API, docs and package metadata, documenting findings, corrections and accepted residual risks in the PR. AI review is supporting evidence, not independent human sign-off. Seek optional outside review for high-risk changes when available.
3. **Completed for 0.1:** the release owner expressly accepted the lossless machine-interchange CSV policy and the documented spreadsheet-formula execution-context limitation, closing [#200](https://github.com/infoconex/RecordSift/issues/200). Preserve exact data semantics; classify and resolve or accept any **new** release risk before GO.
4. Log the sole maintainer's explicit **source promotion GO** for the exact candidate only after all required checks and documented second-pass owner review. This manual GO is not enforced by GitHub's approval count; source promotion remains a separately approved squash PR.
5. Separately obtain **publication GO** after verifying stable version and repository commit metadata, artifact checksum, fresh security/license reviews, and consumer behavior on the exact published artifact. Do not reuse an ephemeral local CI checksum.

## Promotion and publication — explicit authorization required

The release owner explicitly authorized **only** source promotion from `release/0.1` to `main` on 2026-10-31. Promotion must use a reviewed PR with **all three** `main`-targeted workflow gates (Windows full build/NUnit/security/API, independent locally installed RC/stable consumers, and documentation). Rerun all three on the exact post-merge `main` commit. **The authorization does not include creating a tag, GitHub release, uploading a NuGet package, or publishing to any public feed.** Before future publication, separately approve the final distribution channel, confirm final stable 0.1.0 identity/README, rebuild and verify the exact artifact/checksum on the promoted commit, obtain explicit publication authorization, and independently install from the published source. **Successful local stable-package CI is not permission to distribute or reuse its ephemeral checksum as a final release checksum.**

## Rollback

If release checks fail, do not publish. After publication, a defective package should not be overwritten; document the affected version, commit, hashes and affected consumers, halt further distribution, and create a reviewed corrective version or authorized revert PR. Preserve traceability and compatibility notes; do not erase published historical tags as a substitute for an appropriate remediation.
